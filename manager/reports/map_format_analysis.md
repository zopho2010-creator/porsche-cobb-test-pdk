# Map 元数据、容器边界与通用 CRC

本报告对应官方 APManager.exe 3.2.0，SHA-256 `6c4361ed96f75951185a7dfb9d4376234a4a7d594bcc2f28a0f29fa6640c404f`。地址均为原始 PE 的首选 VA，ImageBase `0x400000`。“已验证”表示实际文件、反编译或所列独立计算，不表示真实 Map 样本导入成功。本次没有合法取得的 Porsche 981 `.ptm` / `.ptp` 样本，没有 Accessport 或车辆连接。

## 已验证的命名字段读取

**已验证（`0x7F7C50`）**：函数用 `FUN_0087DD30` 按名称查找节点，经对象可用性和文本指针检查后读取文本，再调用字符串赋值路径写入目标对象。虽然保存文件名是 `decompile_map_fields_writer.json`，它实际显示的是从命名节点**读取字段并填充对象**，不能因文件名把它称为外部文件写入器。

| 字段 | 本次观察到的代码行为 |
|---|---|
| `shortDesc` | 有可读文本时复制到首个字符串成员；缺失或相关检查失败时赋空字符串 |
| `longDesc` | 相同的条件读取及空字符串回退，目标为第二个字符串成员 |
| `vehicleName` | 相同的条件读取及空字符串回退，目标为第三个字符串成员 |
| `vendorName` | 相同的条件读取及空字符串回退，目标为第四个字符串成员 |
| `revision` | 可见调用为 `FUN_0087EEC0("revision", ...)`；返回 0 时将 double 转 float 保存。该调用位于 `vendorName` 成功读取的分支中，不能省略这一条件 |
| `swVersion` | 节点或文本检查失败可直接返回 1；有文本时复制并交给 `0x514840`，再复制其结果对象的成员。未完整恢复其版本字符串语法 |

**边界**：这些路径可以证明 Manager 有 Map 元数据解释和对象填充代码。它们尚未证明外层输入的容器编码、压缩方式、签名、首部布局或字段在 `.ptm` 文件中的固定偏移。字符串操作中的 `0x0F` / `0x10` 分支是内部短字符串存储及分配阈值，不能当作描述文本最多 15 字符的文件格式限制；可见代码存在按实际长度分配和复制的路径。也不能用函数最终返回 1 推导所有命名字段必需或完整验证成功。

**已验证（`0x7F72C0`）**：另一字段读取函数具有以下实际控制流。这里记录的是目标对象的内存偏移，**不是外部 Map 文件偏移**。

| 字段 / 集合 | 本次观察与限制 |
|---|---|
| `vendorID` | 先检查节点和可读文本；仅当字符串长度恰为 4 时向目标对象开头复制 5 字节，包含终止符。长度不符时本分支不执行该复制 |
| `vehicleID` | 节点和文本检查通过后调用字符串赋值辅助函数；不能由字段名称认定其值就是 Porsche 981 型号编码 |
| `romSum` | 节点存在及可用性检查通过后，以 `"value"` 为名调用数值读取辅助函数，目标对象偏移 `+0x38`。这里只读到元数据值，没有从这里识别出 ROM 校验算法 |
| `saveDateTime` | 相同条件下读取 `"value"`，目标对象偏移 `+0x70`；时间单位、纪元和外部编码尚未验证 |
| `patches` | 调用集合初始化路径后遍历子节点，读取 `romOffset`、`ramOffset`、`length`；有文本载荷时交给 `0x87C140` 转换，特定返回分支才追加；无文本时也有追加路径 |
| 补丁记录 | 可见容器项步长 `0x18`，前三个 32 位成员保存上述三个数值，后面是载荷容器状态。它是进程内记录布局，不能等同于磁盘记录结构 |
| `features` | 遍历名称 / 值对，可见 `atoi` 将值转为整数，随后通过目标对象 `+0x48` 的接口加入集合；没有据此证明严格的整数输入校验 |
| `ramVersion` | 条件读取后检查特征集合是否已有 `ram_version`；缺少时有添加该名称和值的路径 |

**边界**：`0x87C140` 的完整转换语法未在本报告恢复，不能直接命名为已验证的某种编码器。可见代码存在容器扩容、复制和分配溢出处理，但没有证明 `romOffset + length`、`ramOffset + length` 与实际车辆镜像大小一致，也未证明所有补丁文本长度均与 `length` 交叉验证。没有实际输入样本时，不把这些字段实现成可写 ECU 的补丁应用器。

该函数还存在其他对象和调用。本研究只记录上面的非受保护字段处理，不分析受保护类或提取密钥，不把未知变换写成已经恢复的算法。

## MapFile 对象与内部序列化的区别

**已验证（`0x7F63A0`）**：构造函数写入 `Maps::MapFile::vftable`，将对象 `+0x04` 设为 `0xE6`，初始化字符串状态，调用 `0x4C96F0` 和 `0x7F6450`，并将若干末尾成员清零。`0xE6` 在此处是内存成员的初值；没有证据可把它定义为 `.ptm` 文件 magic、版本或长度。

**已验证（`0x7EF9C0` → `0x7EA8A0`）**：导出名称明确对应 `boost::archive::detail::iserializer<boost::archive::binary_iarchive, APMapMetaData>::load_object_data`，其函数体调用 `0x7EA8A0`。定向反编译中能看到重复的对象读取辅助调用、4 字节及 8 字节流读取和流状态错误分支。

这里属于**内部 APMapMetaData 对象 / 索引缓存的序列化路径**。官方手册也说明本地 Map 详情和搜索位置会保存供下次启动使用。它不证明外部 `.ptm` / `.ptp` 整个容器采用 Boost binary archive，更不能把流读取时的对象内偏移拼接成外部格式首部。`0x7EA8A0` 的定向反编译含未完整恢复的参数与调用约定，不能据此给出可互操作的完整缓存格式规范。[官方 Manager 手册](https://cobbtuning.atlassian.net/wiki/spaces/PRS/pages/28246235/Accessport+Manager+Manual)

**文档支持，静态链尚未完整验证**：官方手册说明 `.ptm` 为单 Map 文件，`.ptp` 为 Map Pack 容器；传输时会选取适合已安装 Accessport 的 Map，也提供独立 `Unpack Map Pack` 功能，Porsche 被列为多 ECU revision 的示例。本次对 `.ptp` 引用的定向根函数 `0x4A6840` 恢复了 UI 选择索引和范围检查；其可见体不足以证明完整容器拆包实现。初始 `xref_ptp.json` 的引用结果为空也不能证明拆包代码不存在。[官方 Map Packs 说明](https://cobbtuning.atlassian.net/wiki/spaces/PRS/pages/28246235/Accessport+Manager+Manual)

因此本项目没有虚构外部 `.ptm` 首部，没有实现猜测的 `.ptp` 拆包器，也没有用合成文件冒充合法 COBB Map 的兼容测试。

## 通用 CRC 的实际确认

**已验证（原始 VA `0x87AE50`）**：`targeted_followup/0087ae50.asm` 显示初态 `0xFFFFFFFF`，逐字节执行 `state = (state >> 8) ^ table[(byte ^ state) & 0xFF]`，表位于 VA `0xBFD9A8`，函数返回前没有最终异或。该函数用参数中的指针读取长度，底层循环是先处理字节再比较结束位置的 `do/while`。

`crc32_self_check.json` 记录了对全部 256 个原始表项的比较：与反射多项式 `0xEDB88320` 生成的表完全一致。本次再次从原始 PE 读取表并独立复算，非空测试输入结果为：

| 输入 | 本函数状态值 | Python `zlib.crc32` |
|---|---|---|
| ASCII `123456789` | `0x340BC6D9` | `0xCBF43926` |

对该非空输入，前者等于后者异或 `0xFFFFFFFF`。这里没有执行第三方函数本身；验证来自原始指令、原始表项与独立计算。**零长度调用未验证，不能将其当作安全的空缓冲区 API。**

**未知（用途覆盖）**：这证明软件包含一种常见 CRC-32 内部状态更新过程；不证明它校验整个 Map 或固件文件，不证明 `romSum` 使用此函数，也不证明任何 Porsche ECU / PDK TCU 镜像校验覆盖、校验字段位置或刷写校验规则。

## 可复用候选与当前缺口

| 候选 | 当前可做 | 仍缺少的验证 |
|---|---|---|
| 命名字段元数据读取 | 保留字段名、条件分支及对象关系作为兼容研究依据 | 外部文件至命名节点的完整入口、合法样本及实际导入结果 |
| Map 元数据索引 | 已确认有内部 Boost 对象加载路径 | 完整缓存文件边界、版本差异和往返验证 |
| 补丁记录模型 | 识别 ROM / RAM 偏移、长度及载荷字段 | 载荷编码、适配关系、镜像范围和设备端应用逻辑 |
| 通用 CRC 更新 | 非空输入及全部表项可以独立复算 | 调用方的真实校验范围、空输入契约及其与容器的关系 |
| `.ptp` 拆包 | 官方文档证明 Manager 提供此功能 | 完整容器解析链、合法 981 包、可重现拆包测试 |

“可复用候选”不是已交付、已授权的解保护工具。公开来源并不自动允许绕过某文件的许可证、设备绑定或签名。取得合法且授权范围明确的 981 样本后，才可验证非受保护元数据或容器处理；目前不绕过认证获取样本，没有调校表地址、ECU / PDK 安全访问、刷写序列或车辆恢复能力的证据。
